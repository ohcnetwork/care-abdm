# 05 — Codebase map (as of 2026-09-19, ADR-011 with its amendments, ADR-013, ADR-014, ADR-015, ADR-016)

Read this before touching code. Every module has one job; keep it that way.

## Backend — `backend/src/abdm/` (Django app, label `abdm`, mounted at `/api/abdm/`)

| Module | Job | Invariant |
|---|---|---|
| `apps.py` | `AppConfig`; `ready()` imports `care_seams` and `signals` | Only place side-effect imports happen |
| `settings.py` | Reads `ABDM_*` env into `plugin_settings` (pattern from `care_token_display`) | Names carry no environment marker; sandbox and production differ by value only |
| `care_seams.py` | Registers with Care: `Patient.extensions["abdm"]`, `Facility.extensions["abdm"]` (typed: `hip_name`, `counters`; link-written (ADR-016): `facility_id`, `facility_name`, `hfr` the registry record snapshot; the resumable `hfr_onboarding`; server-written `hip_id`, `hrp_registered_at`, `last_error`), and the 2 `auto_maintained` identifier configs (`abdm/abha-number`, `abdm/abha-address`) | Extension fields carry `x-ui.render_blacklist`; host forms never render them |
| `models.py` | M1: `AbhaTransaction`, `AbdmProfileShare`. Audit: `AbdmOutboundRequest`, `AbdmCallback`. M2: `AbdmLinkToken`, `AbdmCareContext` (`hi_types` derived from the linked items), `AbdmShareItem` (ADR-013: 1 row per shareable record, `staged → queued → linked`, or `failed` / `excluded`), `AbdmLinkSession`, `AbdmConsent`, `AbdmDataRequest`. M3 (ADR-014): `AbdmConsentRequest` (the ask), `AbdmConsentArtefact` (the permission), `AbdmFetchRequest` (1 health-information request; holds the X25519 private key and our nonce until the push is decrypted or 20 minutes pass), `AbdmFetchedRecord` (1 decrypted bundle; `bundle` emptied at `erase_at`). M4 (ADR-015): `AbdmHprProfile` (user ↔ HPR ID, the person's HPR token), `AbdmHprLogin` (an OTP login in progress), `AbdmHpidTransaction` (the HPID creation wizard; the Aadhaar photo until creation). The per-facility HFR wizard state is not a table: ADR-016 keeps it in `Facility.extensions["abdm"]["hfr_onboarding"]` (photo names, not bytes) | Secrets (X-token, link token, OTP hash, the ephemeral private key, the HPR token) stay here, never in an extension. Ciphertext is never stored |
| `migrations/` | `0001_initial` (rebased with Care develop 2026-09-17), `0002_abdmshareitem` (adds the table and turns every advertised `hi_types` value into a linked item), `0003_hiu_consent_requests` (the 4 M3 tables), `0004_nhpr_hpr_hfr` (the 3 M4 tables; `AbdmHfrOnboarding` was removed by ADR-016 before any deployment) | Must match `models.py` |
| `signals.py` | `post_save(Patient)`: consume `extensions.abdm.txn_id` → identifiers (M1). ADR-013: `post_save(MedicationRequestPrescription \| DiagnosticReport \| ReportUpload)` → `tasks.stage_record` (stage, never link); `post_save(Encounter)` → `tasks.sync_encounter` when `status`/`encounter_class`/`period` change (a closing status links every staged item) | `link_patient_to_transaction` is the single writer of ABHA identifiers. It refuses an ABHA that a different patient record holds: 1 ABHA number is 1 person (`/concepts/phr`). `LinkError` is a DRF `ValidationError`, so every caller answers HTTP 400 with a desk sentence; a plain exception here becomes HTTP 500 in Care's patient viewset |
| `tasks.py` | `dispatch_callback` (verified callback → handler; the M3 handlers are in the same table); `stage_record` (stage 1 record); `sync_encounter` (Encounter change; close → link); `link_care_context` (1 link call for the queued items); `notify_care_context` (delayed notify, F9); `retry_share_items` (periodic, every 5 min: re-queue due items, ADR-013 D4); `hiu_housekeeping` (periodic, every 15 min: fail a health-information request with no push inside its window and tell the gateway; erase bundles past `erase_at`, ADR-014) | A Celery worker must run for M2, M3 and Scan and Share. A refusal is never repeated: it earns `ABDM-1092` |
| `urls.py` | Route table. One catch-all POST route (last) receives every gateway callback: the bridge URL is `<base>/api/abdm`, so a callback lands at `/api/abdm/<callback path>` whatever the path. Mirrors: `frontend/src/lib/careApi.ts`, `bruno/` | Change all 3 together |
| `gateway/session.py` | Gateway session token, Redis-cached, 60 s margin | The token never leaves the server |
| `gateway/outbound.py` | `send()`: every call to ABDM or to an HIU push URL; adds `REQUEST-ID`, `TIMESTAMP`, `X-CM-ID`, `Authorization`, and the facility's gateway service id as `X-HIP-ID` (`role="hip"`, default) or `X-HIU-ID` (`role="hiu"`, M3), or no facility header at all (`role="none"`, the NHPR calls); records `AbdmOutboundRequest`; reads all 3 error envelopes; `failure(row)` gives the `errors.Failure`; keeps the response headers of a refusal in `response_headers` | A 2xx with an `{"error": {...}}` body is a failure. `send()` never raises: a transport failure is recorded and returned, so every caller reads 1 shape. ABDM answers some refusals with an empty body, so the headers are the only evidence (E11) |
| `gateway/certs.py` | Gateway JWKS, cached 6 h, fetched with the gateway bearer token (the sandbox answers 401 without it) | Raises `GatewayCertsError`; the receiver turns it into a 503 |
| `gateway/bridge.py` | Callback URL derivation, `PATCH bridge/url`, live `GET bridge-services` (caches the bridge id 1 h), HRP service registration on `ABDM_HSP_URL` with 1 entry per link type, `HIP` and `HIU` (ADR-015; body from `nhpr/rules.hrp_linkage_body`) | The gateway is the source of truth for bridge state; nothing is snapshotted |
| `gateway/views.py` | `GET gateway/status`, `GET bridge` (staff), `POST bridge/register-url` and `GET admin/overview` (superuser: gateway status, live bridge and services, every facility with its ABDM state through `facility/create.list_facilities`) | Probes never return tokens |
| `callbacks/paths.py` | Pure: callback path → operation id. The real paths carry an `/api` prefix the docs omit (observed 2026-09-17: `{bridgeUrl}/api/v3/hip/token/on-generate-token`); `operation_for_path()` drops it, and the `/v0.5/...` spellings are aliases. M3: the 5 `/v3/hiu/...` callbacks and our own data push path `/v3/hiu/health-information/transfer` | No Django import; a path the docs never named maps to `""` and is still stored |
| `callbacks/receiver.py` | Stores each callback before verification; idempotency key; resolves the operation id through `paths.py` | Never dispatch an unverified callback |
| `callbacks/signature.py` | JWT against the gateway JWKS: configured header first, then any JWT-shaped header; algorithm from the matching JWK (RS256 or RS512); returns the header name; `seconds_late()` reports how late the token was | Fails closed in every environment, but accepts a token that expired inside `ABDM_CALLBACK_SIGNATURE_LEEWAY_SECONDS` (default 3600). The gateway repeats a refused delivery about 16 minutes later with the same, dead token (finding E10) |
| `callbacks/views.py` | Generic callback view (`AllowAny`): store, verify, `202 {}`; 401 on a bad signature, 503 when the verifier cannot run; never raises (Care's `ATOMIC_REQUESTS` would roll the row back). Plus the superuser callback log | The row always survives; `signature_header` and `signature_error` are the evidence |
| `facility/rules.py` | Pure format rules for HFR ID, facility name (typed names only; the registry's own name is stored as-is), HIP name; `find_hip_service()` picks the gateway service row for an HFR id | No Django import |
| `facility/service.py` | Reads and writes `Facility.extensions["abdm"]`. **HIP ID is not the HFR facility ID on the sandbox**: the registry issues `<facilityId>_<n>` (`IN1410000232_1`), the link token names it, and a call sent with the bare HFR id never gets its callback (2026-09-17). `sync_hip_id()` stores the service id read from `gateway-list-bridge-services` (after HRP registration and on every setup-page load); `hip_id_for()` returns it and is empty until a service exists, so an unregistered facility never sends a call the gateway would accept and drop; `facility_for_hip_id()` resolves an inbound HIP ID in any of the 3 forms. ADR-016: `EDITABLE_FIELDS = (hip_name, counters)`; `set_registry_link()` is the only writer of `facility_id`, `facility_name` and the `hfr` snapshot (forgets the HIP ID when the id changes, derives a default HIP name); `get_onboarding()` / `save_onboarding()` hold the HFR wizard state; `is_linked()` | `hip_id_for()` and `facility_for_hip_id()` are the only HIP ID logic |
| `facility/views.py` | `GET/PUT facilities/<id>/abdm` (`PUT` body `{hip_name, counters}`), `POST .../hrp-services` (refuses an unlinked facility). ADR-016 "Add a facility": `GET care/facility-form-options`, `GET hfr/search` (`?facility_id=` or `?name=&state=&district=&page=`), `GET hfr/prefill?facility_id=`, `POST facilities` (`{care, registry_id?, hip_name?, organization?}`) | Facility routes gate `can_update_facility_obj`; the search, prefill and create routes gate Care's `can_create_facility` |
| `facility/create.py` | ADR-016 "Add a facility": `form_options()` (Care's `FACILITY_TYPES`, `FacilityFeature`), `geo_suggestions()` (state and district by name; Care government organizations carry no LGD codes), `prefill()` (record + Care fields + geo + default HIP name + the facility already linked to that record), `create_facility()` (runs Care's own `FacilityViewSet.handle_create` in-process: `FacilityCreateSpec`, `can_create_facility`, root organization and creator's admin role; then `nhpr.facility.link_record`; Care's pydantic errors returned in Care's `{"errors": [{loc, msg}]}` shape; a browser-sent `extensions` dropped; `ALREADY_LINKED` refused before any create), `list_facilities(request, organization=None)` (Care's own visibility; each row with registry status, HIP ID, onboarding status, `last_error` and `last_failure_for()`, for the admin dashboard) | Never trusts a registry record from the browser: `registry_id` is looked up live |
| `abha/*` | M1: `crypto` (RSA-OAEP SHA-1), `checksums` (Luhn, Verhoeff), `client` (1:1 endpoint wrappers), `service` (journeys, X/T/R-token lifecycle), `views` | `service` is the only module that reads or writes user tokens |
| `share/*` | M1 Scan and Share: `rules` (pure), `service` (`handle_profile_share` → token → `on-share` ack), `views` (desk inbox) | Always sends an acknowledgement, SUCCESS or FAILURE |
| `errors.py` | **Pure.** 1 catalogue and 1 `classify()` that turns any failure into what happened, what to do, and whether a repeat helps now, later (with the time) or not at all. Holds `TOKEN_REQUEST_WINDOW` (7 min, finding F6), `CALLBACK_DEADLINE`, the sandbox `OVERRIDES` and the plug's own codes (`NO_ABHA`, `NO_ANSWER`, …). Read ADR-012 first | No Django import. Nothing else may keep a hand-written list of ABDM codes |
| `error_catalogue.py` | **Generated**, do not edit. 818 codes from the 2026-09-15 `/docs/hiecm/v3/reference/error-codes.md`. Rebuild: `python3 scripts/generate-error-catalogue.py`. The 2026-09-16 page dropped the "What to do" column (findings A10), so the script refuses it (exit 2) and the file stays at the last good catalogue | `getting-started/build-it-well` tells every HIP to key its handling to this table |
| `hip/rules.py` | Pure M2 rules: care-context display, gender code, link-token expiry (`exp` or 6 months), OTP hash, date-range check, every request body builder, parsers for the consent and health-information callbacks | No Django import |
| `hip/crypto.py` | Pure data-transfer crypto: X25519 → XOR nonces → HKDF-SHA256 → AES-256-GCM; `decrypt()` for tests and M3 | No Django import |
| `hip/contexts.py` | HIP-initiated route: `ensure_care_context`, `ensure_link_token` (ADR-012 D3 window), `sync_encounter` (close → queue all → link), `link_context`, `request_link` (1 patient block per linked + queued type, F7), `notify_context`, the result-callback handlers; `handle_carecontext_result` settles the queued items and derives `hi_types` | A context becomes `linked` only in `handle_carecontext_result` |
| `hip/discovery.py` | User-initiated route: `handle_discover` (verified ABHA match only), `handle_link_init` (OTP by Care SMS), `handle_link_confirm` | The OTP is stored as a hash; fixed value outside production |
| `hip/sharing.py` | ADR-013: `stage_prescription`, `stage_diagnostic_report`, `stage_discharge_summary`, `stage_op_consultation` (outpatient, with the first record); `queue_items`, `queue_all_staged`, `link_queued`, `on_link_result` (linked, or retry in `LINK_RETRY_INTERVAL_MINUTES` up to `LINK_MAX_RETRIES`), `retry_due_items`, `refresh_hi_types`, `item_summary` | A linked item never changes; a cancelled or drafted record is excluded only before its link |
| `hip/consent.py` | `handle_consent_notify`: store GRANTED / REVOKED / EXPIRED, send `on-notify` ack | The artefact signature is stored, not verified |

| `hip/views.py` | `GET encounters/<id>/care-context` (state + `shareItems`), `POST .../care-context/link {items\|all}` (queue + link; gated on `can_write_encounter` without the closed-encounter rule), `POST .../share-items/<id>/exclude\|include`, `POST patients/<id>/abha/sms-link`, `GET patients/<id>/abha/consents`. `_failure_block()` adds the classified `failure` to the state | Gates from `care/security/authorization/{encounter,patient}.py`. | `hiu/rules.py` | Pure M3 rules: the 6 purposes and 8 HI types, the defaults (12 months, 30 days), `validate_request()` (clamps `date_to` to now: the HIE-CM refuses a future `dateRange.to`, findings L9), every HIU request body builder (`consent_request_body`, `consent_notify_ack_body`, `hi_request_body`, `key_material_block`, `hiu_notify_body`, …), the parsers of the 5 callbacks and of the push, `bundle_summary()` (HI type off `Composition.meta.profile`), `artefact_is_live()` | No Django import. | `hiu/service.py` | ADR-014: `create_consent_request` (init call, `role="hiu"`); handlers `handle_on_init`, `handle_on_status`, `handle_consent_notify` (GRANTED → artefact rows → ack → `fetch_artefact`; DENIED / EXPIRED / REVOKED → settle and erase), `handle_on_fetch` (detail → `request_health_information` with a fresh key pair), `handle_hi_on_request` (transaction id), `handle_transfer` (decrypt with the transaction's key, MD5, store `AbdmFetchedRecord`, notify RECEIVED / FAILED after the last page, scrub the ciphertext from the stored callback); `refresh`, `fetch_again`, `housekeeping`, `search_providers`; the desk summaries (`hiu_state`, `record_detail`) | The private key leaves the row the moment the push is decrypted or the window passes. Why `txn_id` and not the ABHA number from the client: a client-supplied ABHA would be forgeable.
Why `post_save` and not a post-create callback: core drops `auto_maintained` identifiers on create
(`care/emr/api/viewsets/patient.py:138`) and the `PatientRegistrationForm` slot has no post-create hook.

## Data flow — HIP-initiated link (M2 journey 1)

1. Encounter saved → `signals.sync_encounter_care_context` → `tasks.sync_encounter` after commit.
2. `hip.contexts.sync_encounter`: facility set up? patient has ABHA? `available_hi_types` non-empty? → `AbdmCareContext` row.
3. No usable link token → `m2-generate-link-token` (202); the token lands on `/v3/hip/token/on-generate-token` → `AbdmLinkToken.active` → `link_pending_contexts`.
4. `m2-hip-link-care-context` with `X-Link-Token` (202) → `link_requested`.
5. `/v3/link/on_carecontext` → `linked` (or `failed` with the gateway code) → `m2-link-care-context-notify` → `/v3/links/context/on-notify` → `notified_at`.

## Data flow — consent and transfer (M2 journey 4)

1. `/v0.5/consents/hip/notify` (or `/api/v3/consent/request/hip/notify`) → `AbdmConsent` → `m2-consent-hip-on-notify` ack.
2. `/v0.5/health-information/hip/request` → `AbdmDataRequest` (deadline = received + 20 min) → validate → `m2-hip-health-information-on-request` ACKNOWLEDGED or ERRORED.
3. `transfer()`: for each linked care context of the consent in the requested range × each consented HI type with data → `build_bundle` → MD5 → encrypt → 1 push to `dataPushUrl` → `m2-hip-data-flow-notify` TRANSFERRED or FAILED.

## Data flow — HIU consent and fetch (M3, ADR-014)

1. Desk `POST patients/<id>/abha/consent-requests` → `AbdmConsentRequest` → `m3-consent-request-init` (202, `X-HIU-ID`).
2. `/v3/hiu/consent/request/on-init` → `consent_request_id`. The desk may `refresh` → `m3-consent-request-status` → `/v3/hiu/consent/request/on-status`.
3. `/v3/hiu/consent/request/notify` GRANTED → `AbdmConsentArtefact` rows → `m3-consent-notify-ack` → `m3-consent-fetch` per artefact → `/v3/hiu/consent/on-fetch` → detail stored.
4. A live artefact → `AbdmFetchRequest` (new X25519 key pair, our nonce, `dataPushUrl`, 20-minute deadline) → `m3-health-information-request` → `/v3/hiu/health-information/on-request` → `transaction_id`.
5. The HIP posts to `/api/abdm/v3/hiu/health-information/transfer` (signed catch-all) → `handle_transfer`: decrypt, MD5, `AbdmFetchedRecord` per entry → after the last page `m3-health-information-notify` RECEIVED / FAILED; key blanked; ciphertext scrubbed.
6. DENIED / EXPIRED / REVOKED (notify or on-status) → artefacts settled, records erased. `hiu_housekeeping` erases bundles at `erase_at` and fails a request with no push inside its window.
