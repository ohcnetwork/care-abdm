# Findings about the docs site (for the documentation team)

This file is a register. Each finding has 1 row: an ID, the date it was raised, a status, the
statement, and the URL that should have answered the question. Statuses:

- **Open** — the docs still do not answer it.
- **Resolved** — the docs now answer it, or the sandbox settled it. The row says how and when.
- **Positive** — the docs were right and the sandbox agreed.
- **Withdrawn** — the entry was a design question for this plug, not a docs gap.

Scrubbed 2026-09-17 against the docs mirror fetched 2026-09-17 from the live site
(`abdm-docs-mirror/MANIFEST.json`, 382 pages); the previous scrub was 2026-09-15. Rows A10–A12, B19
and E15 were added on 2026-09-19 after the site republished (450 pages, catalogue 2026.09.16); the
older rows keep their pre-2026-09-16 page names, which still serve at their old URLs (A12). Stale rows were
corrected, one duplicate was merged, and section J citations were re-checked against the host repos.
The pre-scrub file is kept in the session archive, not in the repo. Rows A13–A15, N16–N22 and J9 were
added on 2026-09-21 after the mirror rebuild (the skills' new `design.md`) and the first M4 calls on the
sandbox; N1, N2, N4, N7, N8 were resolved or narrowed by 40 read-only probes the same day.
Base URL for every source: `https://abdm-docs.dev.eka.care/docs/hiecm/v3/`.

- 2026-09-10 — Care-context reference number = `Encounter.external_id`; display = `<OPD|IPD|class> records for <day>`; discovery matches on verified ABHA address or number only (ADR-008 decisions 2-4).
- 2026-09-14 — `X-HIP-ID` is derived by the plug, never client-supplied. Superseded 2026-09-17: it is the service id the gateway holds for the facility (E1), read from `gateway-list-bridge-services` and stored on the facility; a facility with no service is not configured for M2.
- 2026-09-15 — The bridge id is read live from the gateway and cached; no snapshot table (ADR-011). The bridge UI is instance-level at `/admin/abdm`, not on a facility page (Rithvik).
- 2026-09-15 — Day-1 record types: OPConsultation, Prescription, HealthDocumentRecord (ADR-011). Superseded 2026-09-18 (ADR-013): OPConsultation (outpatient only), Prescription (`MedicationRequestPrescription`, not draft), DiagnosticReport (final), DischargeSummary (generated PDF); HealthDocumentRecord removed.
- 2026-09-18 — Records are staged, not linked, when a clinician saves them. The desk links selected records on the ABDM tab; a completed or discharged Encounter links every staged record; retries hourly, 3 times (ADR-013).
- 2026-09-19 — M4 (ADR-015): all 4 tiers; the gateway session token is the bearer for every NHPR call; the HPR token is per user, held server-side, by password or Aadhaar OTP; 1 HPR ID per Care account; the HFR card and wizard live on the setup page, "My HPR ID" under the user menu; the full register-professional form; the Aadhaar photo is dropped once the HPID exists.
- 2026-09-19 — Facility onboarding UX (ADR-016): nobody types a registry value (the HFR id and the registered name come only from a registry link: lookup, search, the HFR wizard, or "Add a facility"); no new table (the registry snapshot and the HFR onboarding state live in `Facility.extensions["abdm"]`; `AbdmHfrOnboarding` removed); 1 registry card on the setup page; the host `AddFacilitySheet` is replaced through the host's component-override registry (`REACT_MFE_REGISTERED_COMPONENTS=AddFacilitySheet`, no host change); "Add a facility" offers already-in-the-registry, not-yet, Care-only; state and district matched by name, the person picks the leaf; the Care facility type is a confirmed suggestion (Rithvik). Later the same day: no ABDM organization tab; the facility overview and "Add a facility" live on the ABDM admin dashboard's Facilities card; the wizard is `/abdm/facilities/new` with optional `?organization=` (Rithvik).
- 2026-09-21 — Developer mode (ADR-018): the switch is the env var `ABDM_DEVELOPER_MODE=true`, instance-wide (Care's `UserFlag` offered and declined); any authenticated user may open the explorer when it is on; the M1 ABHA-service calls, the gateway session and the JWKS read join the audit table with every secret redacted at write; the JSON tree is written in the plug; replay, copy-as-curl, docs links and request preview are a 2nd pass (Rithvik).
- 2026-09-22 — Developer-mode surfaces wear a console skin (ADR-018 amendment): a scoped token block `.dark.abdm-console` (navy, cyan accent, Geist Mono from careui), dark in both host themes, terminal furniture in `dev/console.tsx`. A clinical surface never wears it; a dark strip on a clinical page means developer mode is on in that deployment.
- 2026-09-21 — After an outbound call, a view returns the failure and never raises it (J9). A refused M4 call shows the registry's own words with the code and the REQUEST-ID (`abdm-m3/design.md`); the ADR-012 desk sentences stay for the patient-facing M2 surfaces. The callback detail API redacts credential headers by name and length (`abdm-m2/design.md`).
- 2026-09-19 — M3 as HIU (ADR-014): the UI is the 3rd card of the ABDM Records encounter tab; a fetched bundle is stored and its content erased at the consent `dataEraseAt` or on revoke, deny or expiry; a request goes to every HIP unless the desk picks 1 provider; defaults CAREMGT, 7 clinical types, 12 months, 30 days, editable; the grant runs the fetch, the data request, the decryption and the notify by itself.
